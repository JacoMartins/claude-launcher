    03 · On screen
    
What the home screen is made of

    
Everything you see lives in one window. HomeActivity builds a single root view, DragLayer, and stacks the rest inside it, back to front. The home grid is made of classic Android Views (fast, precise for drag and drop); menus, panels and the Apps screen are Jetpack Compose, layered on top.

    
Window (edge to edge, wallpaper shows behind)
└─ DragLayer   ui/home/DragLayer.kt · takes drags, pinches, swipes
   ├─ HomeScreenLayout   ui/home/HomeScreenLayout.kt
   │  ├─ Workspace   horizontal pages, spring scrolling
   │  │  └─ CellLayout × pages   the grid; places items by cell
   │  │     ├─ AppIconView   icon + label + badge, drawn by hand
   │  │     ├─ FolderIconView   normal or large (2x2) folder
   │  │     ├─ LauncherWidgetHostView   one app widget
   │  │     └─ WidgetStackView   swipeable stack / slideshow
   │  ├─ PageIndicatorView   house + dots
   │  └─ Hotseat (a CellLayout)   the dock
   ├─ ComposeView → AppDrawer   the Apps screen, slides up
   ├─ ComposeView → HomeOverlay   menus, folder panel, edit bars, picker, undo
   ├─ DragView   the image under your finger while dragging
   └─ ResizeFrame   handles around a widget being resized

From database to screen

      
How the home screen appears and stays up to date. Nothing on home is drawn from memory alone: the database is the source of truth, and every change flows back through it.

      
flowchart LR
  DB[(Room pages, items)] --> HR[HomeRepository compute]
  AR[AppRepository installed apps] --> HR
  SS[SettingsStore grid, mode] --> HR
  HR --> LR[LayoutResolver keeps grid valid]
  LR --> HS[[HomeState StateFlow]]
  HS --> HA[HomeActivity.bind]
  HA --> V[Views on the pages]


      
  1. LauncherApp starts once per process and creates the two layout databases, settings and the app list.
    LauncherApp.kt
  2. HomeRepository combines the database tables, the installed apps and the settings into one flow.
    data/HomeRepository.kt · compute()
  3. LayoutResolver places every item: drops apps that were uninstalled, re-places items that no longer fit the grid.
    model/LayoutResolver.kt
  4. The result is a HomeState: a list of entries (apps, folders, widgets, stacks), each with its page and cells.
    HomeState, HomeEntry
  5. HomeActivity collects that state and binds it: it reuses each item's view by id, moves it to its cell, and removes views of items that are gone.
    HomeActivity.kt · bind()

    

    

      
Life of a drag

      
Long-press an app, move it, let go. The drag is handled entirely in Views, then saved through the repository, then the screen updates from the new state.

      
flowchart LR
  LP[Long-press AppIconView] --> ARM[DragController.arm]
  ARM --> DL[DragLayer finger moves]
  DL --> UP[DragController.update]
  UP --> DEC[DropLogic.decide]
  DEC -->|hint| CL[CellLayout drop hint]
  DL -->|let go| FIN[finish → DropResult]
  FIN --> OD[HomeActivity.onDropped]
  OD --> REP[HomeRepository.place one transaction]
  REP --> DB[(Room)] --> ST[[HomeState]] --> BIND[bind]


      
  1. A long-press shows the item's menu and arms a drag with a snapshot image of the item.
    HomeActivity · onItemLongPress → drag.arm
  2. Once the finger moves, DragLayer starts the drag: the item hides, a DragView follows the finger.
    ui/home/DragLayer.kt · DragController.begin
  3. On every move, the controller finds the cell under the finger and asks DropLogic what a drop there would do: move, push aside, swap, make a folder, join a stack.
    ui/home/DragController.kt · model/DropLogic.kt
  4. Holding at a screen edge flips the page; dragging from an open folder reorders inside it until the finger rests outside.
    DragController · pageFlip, leave
  5. On release the result goes to the activity, which moves the views at once (so nothing flashes) and asks the repository to save.
    HomeActivity · onDropped, optimisticMove
  6. The repository writes in one database transaction and keeps an undo snapshot; the new HomeState rebinds the screen while the drag image flies into the item's new spot.
    HomeRepository.place · DragController.finish

    

    

      
How glass is drawn

      
Android does not let ordinary apps read the wallpaper, so Canyon UI keeps its own copy of the photo it sets, blurs it, and draws it behind see-through surfaces lined up with the real wallpaper.

      
flowchart LR
  WA[WallpaperActivity pick photo] --> SP[WallpaperBackdrop setFromPhoto]
  SP --> WM[WallpaperManager setBitmap]
  SP --> CP[copy on disk + in memory]
  CP --> BL[blur per mode]
  BL --> AC[[active StateFlow]]
  AC --> GS[GlassShader views, Android 13+]
  AC --> CPU[plain blur views, fallback]
  CP --> SRC[BackdropSource Haze source]
  SRC --> HZ[Haze glass / blur Compose panels]


      
  1. The chooser hands a photo to WallpaperBackdrop, which crops it to the screen, sets it as the wallpaper and keeps the image.
    WallpaperActivity.kt · ui/design/WallpaperBackdrop.kt
  2. It shrinks and box-blurs a copy for the current mode: half resolution for glass, much smaller for frosted.
    WallpaperBackdrop.blur()
  3. View surfaces (folders, edit pages, widget cards, stacks) draw that copy behind themselves at their exact screen position, and redraw when they move.
    WallpaperBackdrop.draw() · track()
  4. In glass mode on Android 13+, the copy goes through an AGSL lens shader that bends it at the rim.
    ui/design/GlassShader.kt
  5. Compose panels use Haze instead: an invisible full-size copy of the wallpaper is the source, and each panel applies Haze's glass or blur over it.
    ui/design/Backdrop.kt · BackdropSource, backdrop()
  6. If the wallpaper is changed elsewhere, the copy no longer matches, so it is dropped and surfaces fall back to translucent.
    WallpaperBackdrop.listen() · check()

    

    

      
Adding a widget

      
Widgets belong to other apps. The launcher only hosts them, so adding one is a short negotiation with Android and the widget's app.

      
flowchart LR
  PK[WidgetPicker] --> SA[HomeWidgets.startAdd]
  SA --> ID[allocate id]
  ID --> BIND{allowed to bind?}
  BIND -->|no| ASK[ask the user]
  BIND -->|yes| CFG
  ASK --> CFG{setup screen?}
  CFG -->|yes| RUN[run widget setup]
  CFG -->|no| ADD
  RUN --> ADD[HomeRepository.addWidget]
  ADD --> VIEW[LauncherWidgetHostView + WidgetFrame]


      
  1. The picker lists every widget with a preview (image, layout or Android 15's generated preview) at its starting size.
    ui/overlay/WidgetPicker.kt · ui/widget/WidgetCatalog.kt
  2. Choosing one allocates a widget id from the host and asks Android to bind it; the first time, Android asks you to allow it.
    HomeWidgets.startAdd
  3. If the widget has a setup screen, it runs; cancelling releases the id again.
    HomeWidgets
  4. The repository saves the widget in its cells, and bind creates its host view with the rounded frame and border.
    HomeRepository.addWidget · ui/widget/WidgetFrame.kt
  5. The widget is told its size (and dark mode) so it can pick a matching layout; one-row widgets get the whole cell's size.
    ui/widget/WidgetSizes.kt · applySize
